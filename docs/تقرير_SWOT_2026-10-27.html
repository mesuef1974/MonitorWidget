مرصد الجهاز: تحليل SWOT للويدجت والتطبيق

تقييم الوضع الحالي لـ MonitorWidget (الخادم المحلي، واجهة الويب، الويدجت WPF، والغلاف WebView2) مبني على قراءة المستودع عند main بعد PR 13 مع PR 14 وPR 15 مفتوحين.

الخلاصة التنفيذية. المنتج ناضج وظيفيًا وأمنيًا بما يفوق حجم فريقه، لكن استدامته هي نقطة الضعف: ثلاثة ملفات ضخمة تحمل معظم المنطق، وطبقة الويدجت مكتوبة بلغة غير مخصصة لواجهات WPF، واعتمادية WebView2 مستعارة من تثبيت Teams. الأولوية القادمة ليست مزايا جديدة بل تثبيت ما بُني: تجزئة الخادم، فحوص للويدجت، وإغلاق البنود المعلّقة غير المُتحقَّق منها.

نقاط القوة

  • نموذج أمني محلي محكم: الخادم يرتبط بـ 127.0.0.1 فقط، تذاكر لمرة واحدة تُستبدل بجلسة HttpOnly، تأكيد خادمي (428 + رمز مقيّد بالمسار والمعاملات) لكل عملية هدّامة، وقائمة عناصر محمية لا تُكتب أبدًا.
  • صفر اعتماديات: Python قياسي فقط وSQLite مدمج؛ لا pip ولا حزم تُحدَّث أو تُخترق.
  • تغطية وظيفية واسعة: ذاكرة، مساحة وتنظيف، عمليات، GPU/CPU/IO، طاقة، بدء التشغيل، اعتمادية، WSL، تنبيهات ومهام مجدولة.
  • هوية بصرية واحدة: الويدجت والغلاف والويب تقرأ ألوانها من tokens.css؛ CSS مركزي بفحص آلي يمنع الأنماط المضمّنة والألوان الخام.
  • ويدجت لا يتجمد: الاستطلاع في runspace خلفي، عتبات من الخادم، مفاتيح تنظيف حقيقية مع شريط تأكيد مضمّن.
  • انضباط هندسي: main محمي، PR + CI، squash، Conventional Commits، وبطاقة تسليم آلية بين الجلسات.
  • عربية RTL أصيلة في كل الطبقات، لا ترجمة لاحقة.

نقاط الضعف

  • تركّز المنطق: server.py 1731 سطرًا، widget.ps1 1094، وweb/index.html ملف واحد بكل الـ JS. كل تعديل يلمس الجميع.
  • WPF داخل PowerShell: لا اختبارات وحدة للويدجت، أخطاء XAML تظهر عند التشغيل فقط، وتصحيحه بطيء.
  • اعتمادية هشة: مكتبات WebView2 تُنسخ من مجلد Teams؛ إن غاب أو تغيّر يسقط الغلاف إلى Edge.
  • ديون معلّقة غير مُتحقَّق منها: أزرار معاينة/تنظيف المساحة بعد التقسيم، قائمة الويدجت الجديدة وألوانه، فتح الغلاف من الويدجت، وإخفاء/تأجيل التوصيات الذي لم يُنقل من الصفحة القديمة.
  • فحص فاشل معروف: قاعدة delivery-optimization وصفها يناقض حالتها.
  • الفحوص سكربتات لا إطار: لا تقارير تغطية، ولا فحص لواجهة الويب في المتصفح داخل CI.
  • صلاحيات المسؤول مطلوبة لبعض القياسات (nvidia-smi) وإعادة التشغيل يدوية عبر سكربت.

الفرص

  • تجزئة الخادم إلى وحدات حسب المجال (ذاكرة، مساحة، عمليات، أمن) مع إبقاء الواجهة كما هي؛ خطوة منخفضة المخاطر عالية العائد.
  • نقل الويدجت إلى مضيف مترجَم (.NET/C#) مع بقاء الهوية من tokens.css؛ يحل الاستقرار وقابلية الاختبار معًا.
  • تحزيم رسمي: مثبّت موقّع أو winget، تضمين WebView2 Runtime بدل الاستعارة من Teams، وتحديث ذاتي.
  • اختبارات واجهة: Pester للـ PowerShell وPlaywright لصفحات الويب التسع عشرة داخل CI، مبنية على سكربتات tour الحالية.
  • تقارير دورية: DISM الشهري وتقرير الاعتمادية موجودان؛ يمكن تحويلهما إلى ملخص أسبوعي يُرسل إشعارًا.
  • تكامل نظام: إشعارات Windows Toast وأيقونة شريط النظام بدل الاعتماد على الويدجت الظاهر.

التهديدات

  • تغيّرات المنصة: تحديثات Windows أو PowerShell أو WebView2 قد تكسر الويدجت أو الغلاف دون تغيير في الكود.
  • هدف محلي عالي القيمة: خادم يملك مسارات إيقاف، وحصد عمليات، وتنظيف؛ أي برمجية خبيثة محلية ستستهدفه. التأكيد الخادمي يخفف لكنه لا يلغي الخطر.
  • مضادات الفيروسات: سكربتات تقتل عمليات وتحذف ملفات قد تُصنَّف مشبوهة وتُعزل.
  • زحف النطاق: 46 مسارًا و19 صفحة بمطوّر واحد؛ كل ميزة جديدة تضيف سطح صيانة.
  • خطر الشخص الواحد: المعرفة تعيش في جلسات العمل؛ بطاقة التسليم تخفف لكن لا توثيق معماري مستقل.

أولويات التنفيذ المقترحة

1

إغلاق المعلّق

تجربة أزرار المساحة، قائمة الويدجت، فتح الغلاف من الويدجت، ونقل إخفاء/تأجيل التوصيات. إصلاح delivery-optimization بقرار صريح: تعديل الوصف أو القاعدة.

2

دمج PR 14 وPR 15

كلاهما جاهز؛ يثبّتان التخطيط وآلية الاستمرارية قبل أي عمل بنيوي.

3

تجزئة server.py

مسارات API إلى وحدات حسب المجال خلف نفس الموجّه؛ بلا تغيير في العقد أو الواجهة؛ check_all يثبت التكافؤ.

4

اختبارات الويدجت والويب

Pester للدوال المنطقية في widget.ps1، وPlaywright لالتقاط الصفحات التسع عشرة في CI مبنيًا على tour.cjs.

5

تحزيم مستقل

WebView2 Runtime مضمّن أو مُثبَّت رسميًا بدل نسخ مكتبات Teams، ثم مثبّت موقّع.
